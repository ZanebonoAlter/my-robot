## 0.6 openspec change 标准编排流程（主线程调度模型）

> **主线程只做调度与进度跟踪，重活派发子线程**。子线程模型选型见根 `AGENTS.md`「子线程派发参考」。

### 编排六步

| 步 | 执行者 | 动作 | 产出 |
| ---- | -------- | ------ | ------ |
| 1 | 主线程 | 读 change 制品 + 本规范相关章节 + 受影响代码建立上下文；**跑 `bash scripts/doc-impact.sh suggest` 做文档域预勾选 + 跑 `bash scripts/doc-impact.sh context` 双源注入（业务规范 what：flow「业务约束与不变量」+ 执行规范 how：standard「## Requirements」，必读）** | 变更上下文 + 文档域预勾选 |
| 2 | 主线程 | 按 opsx-apply 约束编写实现计划；**确认 suggest 预勾选后，以 `<!-- doc-impact: 域列表 -->` 机器可读注释写入 tasks.md 文档节** | 实现计划 + doc-impact 声明 |
| 3 | 子线程 | 执行计划（按根 `AGENTS.md` 模型表选型派发） | 代码 + 测试 |
| 4 | 子线程/主 | 人工聚焦 review（见下「review 执行要点」）。⚠️ `ocr`/open-code-review 在本仓库因路径幻觉致 `file_read failed` 连环超时、零有效输出**已弃用**，详见 [`ocr 弃用记录`](../experience/ocr-review-pitfalls.md) | review 意见 + 修复 |
| 5 | 子线程 | 验收门禁：门禁命令(§4.1/§5.1) + `check-standards`(§11.4) + 文档更新(含 §12.2 变更溯源) + 集成测试(§6) | 全绿 |
| 6 | 主线程 | 全程调度 + 进度跟踪（使用 TODO.md / 本地计划文件），不亲自写实现代码 | 进度可见 |

### 何时偏离

- **纯文档 change**：跳过步骤 3 代码实现与步骤 4 review，步骤 5 走 §11.3 grep 一致性校验，其余不变
- **单文件小修**：步骤 2 计划可极简，但仍须走 review + 门禁，不得跳步
- **疑难/架构级**：步骤 1 上下文建立加重，必要时主线程亲自做步骤 2 计划

### review 执行要点（步骤4，子线程聚焦 review）

ocr 弃用后走**子进程聚焦 review**：

1. **精读高风险文件**（挑 5-8 个，不逐行读全部）：并发/缓存（`sync.Once`/`sync.Mutex`/全局单例查「首次失败是否被永久缓存」）、错误处理（被忽略的 error 返回值是否有 nil 解引用风险）、raw SQL（`.Raw()`/`.Exec()` 是否参数化 `?` 占位符）、agent loop/状态机（去重/上限/不变式防御是否齐全）、handler（`:id` 取出的资源是否属于路径 `:xxxId`，防 IDOR）、事务/竞态（read-then-write 是否原子，应用 `clause.OnConflict` 或事务+锁）
2. **`grep` 全包验证关键不变量**：把 change 声明的不变量转成 grep 命令跨改动包验证（如 `grep -rn 'UpsertX\|X{' service/` 确认某路径不调写操作）
3. **按 High/Medium/Low 分类汇报**：High（bug/安全/清晰错误）必修；Medium（合理但依赖上下文）选修；Low（误报）静默丢弃（ocr/open-code-review 本仓库因路径幻觉零产出，已弃用）

### 收到 review 意见后（author 纪律，加载技能 `receiving-code-review`）

- **先验证再改，禁阿谀**：不说「你说得对／好建议／谢谢」，直接改并说明改了什么（Actions > words）；验证前不实现
- **不清楚全停**：有条目没看懂就停下来问，不要先改清楚的（条目可能相关，部分理解=错误实现）
- **YAGNI 检查**：意见要你「正经实现」时，先 grep 实际调用，没人用就删而不是加
- **该 push back 就 push back**：意见在本代码库不成立/破坏现有/与架构决定冲突——用技术理由反驳（引用工作测试或代码），架构级拉用户；外部或自动 review 工具的意见同样先怀疑、验证再定
- **自己 push back 错了**：事实陈述纠正，不长篇道歉

### 主线程纪律

主线程只调度不写实现代码（除纯文档/单行修）；用 TODO.md 或本地计划文件跟踪进度；子线程返回后**必须核验**实际改动。

## 1. 任务拆解规范

apply 启动时将 proposal 垂直切片为 tasks.md 可独立交付子任务；每个子任务含验收标准 + 关联 checkbox；配了 issue tracker 的同步建 issue。

## 2. 实现纪律 — TDD

> 完整 red-green-refactor 工作流加载技能 `test-driven-development`；测试失败难定位加载技能 `systematic-debugging`（四阶段根因调查，未确认根因前不得乱改）。

**铁律：没有失败测试，不写产品代码。**

| 场景 | 要求 |
| ---- | ---- |
| 新增模块 / 核心逻辑变更 | 强制完整 TDD |
| Bug 修复 | 强制先写复现测试，再修代码 |
| 现有代码小幅修改 | 至少补充回归测试 |
| 纯配置 / SQL 迁移脚本 | 豁免（但需人工验证） |

**红旗（遇到即停）**：先写实现后补测试 / 一次生成多个测试 / 测试立即通过没看到失败 / 「这次先跳过 TDD」——删除已有代码，从 TDD 重新开始。

## 3. 复杂设计验证（先脑暴 → 后原型）

设计边界不清 / 需求多解 / 交互形态未定时，先加载技能 `brainstorming` 做纯对话探索（澄清意图、列方案、定取舍，**不出代码**），收敛后再进实现。

涉及状态机（≥3 状态循环流转）/算法逻辑/多模块交互协议（API 契约/事件总线）**必须先做可丢弃原型**：输出方案对比+选型理由+风险点入 `openspec/changes/<name>/`，确认后销毁再进 TDD。

> brainstorming 是「先聊清楚」（轻、纯对话），原型是「用代码验证」（重、出代码）——不要跳过 brainstorming 直接堆原型。

## 4. 后端执行规范（Go + Gin + GORM）

### 4.0 前置条件

apply 启动时检测，缺失作为首个子任务补齐：`go vet ./...`、`golangci-lint run ./...`、`go test ./...`、`go build ./...` 可正常执行（未装 golangci-lint：`go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@latest`）。

### 4.1 质量门禁

```bash
cd backend-go
golangci-lint run ./... && go vet ./... && go test ./... && go build ./...
```

| 工具 | 用途 |
| ---- | ---- |
| `golangci-lint` | 静态分析（staticcheck/revive/gosec 等） |
| `go vet` | Go 官方静态检查 |
| `go test` | 单元测试执行 |
| `go build` | 编译检查 |

**门禁分层**：增量（pi extension 每回合 `turn_end` 自动跑 `golangci-lint`+`go vet`+`go build`，[`.pi/extensions/quality-gate.ts`](../../../.pi/extensions/quality-gate.ts)；前端只跑 `pnpm lint`）→ 日常验证（agent 手动跑 `go test ./internal/<影响包>` / `pnpm test:unit`）→ 归档全量（§11：`go test ./...`+`go build ./...` / `pnpm build`+`nuxi typecheck`）。增量不跑 `go test`（影响包无法自动判定）也不跑前端 typecheck/build/test（需 cmd.exe，bash hook 脆弱），完整门禁由 §11 兜底。真 Claude Code/Codex 无 pi extension，需手动跑增量门禁。

### 4.2 测试 / lint / 代码规范

权威定义：测试框架/`SetupTestDB`/陷阱见 [`standard/backend/testing.md`](standard/backend/testing.md)；lint 见 [`standard/backend/lint.md`](standard/backend/lint.md)；导入顺序/命名/错误处理/响应格式/包结构/domain 白名单见 [`standard/backend/code-style.md`](standard/backend/code-style.md) + [`standard/backend/package-layout.md`](standard/backend/package-layout.md)（`backend-go/AGENTS.md` 是红线速查入口）。

## 5. 前端执行规范（Nuxt 4 + Vue 3）

### 5.0 前置条件

apply 启动时检测，缺失作为首个子任务补齐：`pnpm lint`、`pnpm exec nuxi typecheck`、`pnpm test:unit`（Vitest + happy-dom）、`pnpm build` 可正常执行（未配 ESLint：`pnpm add -D eslint @eslint/js typescript-eslint`）。

> ⚠️ typecheck/build/test:unit 必须用 Windows cmd 跑（WSL 缺 native binding）；lint 可在 WSL 跑。门禁分层见 §4.1。

### 5.2 测试 / lint / 代码规范

权威定义：Vitest/Playwright 见 [`standard/frontend/testing.md`](standard/frontend/testing.md)；ESLint 见 [`standard/frontend/lint.md`](standard/frontend/lint.md)；组件约定/目录归属/API 归一化/Store/双主题/Anti-Patterns 见 [`standard/frontend/code-style.md`](standard/frontend/code-style.md) + [`standard/frontend/theming.md`](standard/frontend/theming.md)（`front/AGENTS.md` 是红线速查入口）。

## 6. 集成测试规范（Go testcontainer）

- **前置**：Docker daemon 运行中（testcontainer 启动隔离 pgvector 容器 `pgvector/pgvector:pg18-trixie`，进程级单例，Ryuk sidecar 自动销毁）
- **运行**：`cd backend-go && go test ./...`（含集成，需 Docker）；`go test -short ./...`（仅单元）。日常只跑影响包，不跑全量。编写细节（入口/`-short`/`ReimportTestDB`/vector 列陷阱）权威见 [`standard/backend/testing.md`](standard/backend/testing.md)

🛑 **DSN 安全红线（不可违反）**：`testutil` 无默认 DSN、不读环境变量，只能启动隔离容器。**禁止**重新引入「默认数据库连接」或「env 覆盖」——历史事故曾因此误连开发库执行 `TRUNCATE` 清空业务数据。

## 7. 架构体检

### 7.1 codegraph 代码图检查（强制）

每个子任务完成后必须执行：

1. `codegraph impact <修改的符号>` → 影响分析，确认波及面无 HIGH/CRITICAL 风险被忽略
2. `codegraph affected <改动的源文件>` → 变更检测，确认受影响测试文件范围符合预期

- `impact` 返回 HIGH/CRITICAL 风险必须暂停向用户报告，不得忽略
- **已知局限 1**：codegraph 无法追踪 Gin handler 的 `group.GET/POST(..., fn)` 注册模式，会把仅由路由注册引用的 handler 误报为「无调用者」（约 26 个误报）。删除 Gin handler 前必须用 `grep` 二次校验其是否被路由注册引用，避免误删
- **已知局限 2·顺传导链深查**：`codegraph impact` 只显示**直接调用面**，看不到跨层/跨域的**隐式传导**（如「改截断排序 → 经 LLM 聚类输入 → 打散 topic 锚定」）。若改动处于某条传导链上（查 [`coupling-map.md`](architecture/coupling-map.md)），必须人工顺链推导下游影响，不能只看到直接 impact 就收工。踩到/分析出新的跨功能传导耦合，**必须往 `coupling-map.md` 补一条**（含守卫测试）

### 7.2 架构合理性检查

退一步做全局审视（zoom-out，不再挂技能）：新增模块与现有系统耦合度、是否引入循环依赖、是否符合现有分层（后端 `internal/{reader,tagmanagement,topicgraph,admin}` + `internal/platform/*`；前端 Vue 3 Composition API + Pinia）。耦合过高则暂停并提出重构建议。

## 8. 变更控制

> apply 阶段允许按需调整 proposal/spec/design/tasks 范围，但调整须**留痕可溯**。

| 程度 | 判据 | 处理 | 与 plan mode 关系 |
| ---- | ---- | ---- | ----------------- |
| 局部澄清/纠错 | 单个 task 实现细节调整、字段名修正、补充边界条件 | 就地改 spec/design/tasks + tasks.md 留痕 | 不需重新 ExitPlanMode |
| 范围扩展 | 新增 1-2 个 task、补遗漏的需求场景 | 就地改 + tasks.md 留痕 + 通知用户 | 不需重新批准，但回复中告知范围扩大 |
| 中等重构 | 重写 >3 个 task、换核心数据结构、改 API 契约形状 | 就地改 + tasks.md 留痕 + **重新 ExitPlanMode 获用户批准** | 需重新批准（plan 核心假设变了） |
| 方向性变更 | 换技术栈、改核心目标、推翻 proposal 根本目标 | **新开 change** 或 archive 旧的 | 新 change 走完整 propose→apply |

> 用户对范围变化有知情权：哪怕就地改，只要扩展了批准范围（新增 task、改了对外契约），必须在回复里明说。

- 禁止在代码注释写「TODO：后续优化」却不记录到 tasks.md
- 归档前禁止跳过 §11 归档门禁；验证节命令未实测通过的 change 不得 archive

## 9. 产出物清单

| 项 | 要求 |
| ---- | ---- |
| 后端门禁 | `golangci-lint run && go vet && go test && go build` 全过 + 变更相关包测试全过 |

## 10. 数据兼容性检查

涉及后端数据层变更时，必须在 tasks.md 增加兼容性验证子任务：

- **PostgreSQL DDL 变更**（GORM AutoMigrate/显式迁移）→ 必须用 testcontainer PG + 历史数据验证迁移（先插历史行再跑迁移，验证回填/NOT NULL/数据完整/索引），或本地起 PG 跑一次迁移看启动 SQL 日志；SQLite 空库迁移**不算**覆盖。model tag 规范见 [`code-style.md`](standard/backend/code-style.md)「GORM model tag 与迁移」，迁移/JSONB 陷阱见 [`testing.md`](standard/backend/testing.md)
- **数据库迁移脚本** → 确认可重复执行（幂等），确认回滚路径
- **GORM 模型字段变更** → 确认 JSON API 响应格式不受破坏性影响
- **配置文件**（`config.yaml`）新增或修改字段 → 同步更新 `docs/reference/configuration.md`

## 11. 归档门禁（Archive Gate）

> 提交前门禁（§4.1/§5.1）覆盖代码质量；归档门禁覆盖「代码↔文档一致性 + 验证可复现」。

### 11.1 归档前置三条件（缺一不可）

> **声称完成前的铁律**（加载技能 `verification-before-completion`）：必须实际跑验证命令并**亲眼确认输出**——不得「看没报错就说过」「命令没跑就说跑过」「上次过了这次肯定过」。归档门禁就是这道理的最后一道关。

1. **测试通过**：§4.1（后端）/ §5.1（前端）/ §6（集成）门禁命令实测通过；纯文档 change 豁免代码测试，但必须在「验证」节附 grep 一致性校验（幽灵路径/调度器/命令、版本号、旧包名零残留）
2. **文档同步**：§9 产出物清单全部勾选，`docs/reference/` 已反映新代码状态
3. **验证可复现**：tasks.md「验证」节（见 §11.2）每条命令实测零失败

### 11.2 tasks.md 验证节强制结构

每个 change 的 tasks.md **必须**以三个固定尾节收尾：

- `## N. 测试` — 本次 change 影响的测试命令（后端 `go test ./internal/<pkg>`、前端 `pnpm test:unit`）
- `## N+1. 文档` — 需同步更新的 `docs/reference/` 文件。**格式**：第一行机器可读注释 `<!-- doc-impact: 域列表 -->`（apply 第 2 步写入，域列表见 `doc-impact.sh menu` 的 8 选项），下方人读 checkbox 列文件。无文档影响写 `<!-- doc-impact: none(理由) -->`。功能性 change 若触及 `flow/`，须声明将在 §12.2 补「变更溯源」链接（archive 后补）
- `## N+2. 验证` — 每条**必须**是「可执行命令 + 期望结果」，禁止只写「已检查」（例：`go test ./internal/admin/scheduler → PASS`）

### 11.4 归档前自检

执行 `openspec archive` 前：

- 重跑 tasks.md「验证」节全部命令，确认零失败（若归档 skill 仅数复选框，归档前由人/AI 手动补这一步）
- 跑 `bash scripts/doc-impact.sh verify <change-dir>` 对账（域注释 + checkbox 文件两层校验）
- 跑 `bash scripts/check-standards.sh`：A-D 段（代码规范结构/domain 白名单/双主题/防孤立引用）+ **F 段（doc-impact verify）** + **G 段（导航层文档死链检查）** 归档前必须零失败；E 段（flow 变更溯源链接）针对 archive 区，归档后校验（见 §12.3）

## 12. 文档流转（Archive 即家 → Flow 反向溯源）

> §11 管 archive **前**门禁；§12 管 archive **后**活文档更新。archive 区是「永久归档家」，靠 `reference/flow/` 反向链接串联。

### 12.1 两段式流转

| 阶段 | 位置 | 责任节点 | 状态 |
| ------ | ------ | ---------- | ------ |
| ① 开发中 | `openspec/changes/<change>/` | propose → apply | 临时，可反复修改 |
| ② 归档（永久家） | `openspec/changes/archive/<date>-<change>/` | `openspec sync` + `openspec archive` | 永久归档，不再搬走 |
| ③ Flow 反向溯源 | `docs/reference/flow/<功能>.md` | archive 后由 change 作者补「变更溯源」行 | 活文档，链接回 archive |

`docs/v1.x/` 里程碑目录**降级为可选**：平时 archive 即终点；发版/做主题合集时才批量收进 `docs/v1.x/changes/`。

### 12.2 变更溯源链接（archive 后强制）

`openspec archive` 完成后，change 作者**必须**在受影响的 `flow/<功能>.md` 尾部「变更溯源」表追加一行链接回 archive 目录，格式如下（「归档位置」列**必须**含 archive 目录全名 `<date>-<change>`，供 `check-standards.sh` E 段校验）：

```markdown
| 日期 | 变更 | 摘要 | 归档位置 |
| 2026-06-14 | scheduler-cron | 定时任务改 cron 驱动 | [archive/2026-06-14-scheduler-cron](../../../openspec/changes/archive/2026-06-14-scheduler-cron) |
```

约定：一个 change 动多个 flow，每个受影响 flow 都补一行；纯文档 change / 不触及任何 flow：豁免（tasks.md「文档」节注明「无 flow 影响」）；链接用相对路径（flow 到 archive：`../../../openspec/changes/archive/<date>-<change>`）。

### 12.3 archive 后校验

补完变更溯源链接后，再跑 `bash scripts/check-standards.sh`，E 段（flow 变更溯源链接）必须零失败。校验范围：新流程生效日（`2026-06-29`）之后的 archive change 必须被某 flow 文档引用；历史存量免校验。

### 12.4 流转完整性自检

archive change 已补溯源链接 + `check-standards.sh` A-G 段零失败 + `docs/reference/` 反映新代码状态。
