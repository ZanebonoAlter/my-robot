## 0.6 openspec change 标准编排流程（主线程调度模型）

> 每个 openspec change 从 apply 到 archive 的标准执行编排。**主线程只做调度与进度跟踪，重活派发子线程**。子线程模型选型见根 `AGENTS.md`「子线程派发参考」。

### 编排六步

| 步 | 执行者 | 动作 | 工具/技能 | 产出 |
|----|--------|------|-----------|------|
| 1 | 主线程 | 建立变更上下文：读 change 制品（proposal/design/specs/tasks）+ 本规范相关章节 + 受影响代码 | `read` / `codegraph_context` / `ctx_search` | 变更上下文摘要 |
| 2 | 主线程 | 按 opsx-apply 约束编写实现计划 | `writing-plans` 技能 | 实现计划文档 |
| 3 | 子线程 | 执行计划（按根 `AGENTS.md` 模型表选型派发） | `executing-plans` 技能 | 代码 + 测试 |
| 4 | 子线程/主 | 代码 review | **人工聚焦 review**：精读高风险文件（agent loop / 并发 / raw SQL / 错误处理）+ `grep` 全包验证关键不变量（见下「review 执行要点」）。⚠️ `ocr`/open-code-review 在本仓库因路径幻觉（幻觉依赖文件路径致 `file_read failed` 连环超时、零有效输出）**已弃用**，不再作为步骤4 工具，详见 [`ocr 弃用记录`](../experience/ocr-review-pitfalls.md) | review 意见 + 修复 |
| 5 | 子线程 | 验收门禁：门禁命令(§4.1/§5.1) + `check-standards`(§11.4) + 文档更新(含 §12.2 变更溯源) + 集成测试(§6) | 本规范各章 | 全绿 |
| 6 | 主线程 | 全程调度 + 进度跟踪（`plan_tracker`），不亲自写实现代码 | `plan_tracker` | 进度可见 |

### 何时偏离

- **纯文档 change**：跳过步骤 3 的代码实现与步骤 4 的 review，步骤 5 走 §11.3 grep 一致性校验，其余不变
- **单文件小修**：步骤 2 计划可极简（一两句），但仍须走 review + 门禁，不得跳步
- **疑难/架构级**：步骤 1 上下文建立加重，必要时主线程亲自做步骤 2 计划而非派发

### review 执行要点（步骤4，人工聚焦 review）

ocr 弃用后，步骤4 走**人工聚焦 review**，比 ocr 在本仓库更可靠。子线程/主线程按下列清单做：

1. **精读高风险文件**（按本次 change 挑 5-8 个，不逐行读全部）：
   - 并发/缓存：`sync.Once` / `sync.Mutex` / 全局单例（查「首次失败是否被永久缓存」）
   - 错误处理：被忽略的 error 返回值（`_, _ :=` / `idx, _ :=`）是否有 nil 解引用风险
   - raw SQL：所有 `.Raw()` / `.Exec()` 是否参数化（`?` 占位符，无字符串拼接）
   - agent loop / 状态机：防御是否齐全（去重 / 上限 / 不变式）
   - handler：路径参数是否校验（IDOR — `:id` 取出的资源是否属于路径里的 `:xxxId`）
   - 事务/竞态：read-then-write 是否原子（应用 `clause.OnConflict` 或事务+锁）
2. **`grep` 全包验证关键不变量**：把 change 声明的不变量（如「review 不回写表 X」「result 不可变」）转成 grep 命令，跨本次改动包验证（如 `grep -rn 'UpsertX\|X{' service/` 确认某路径不调写操作）。
3. **按 High/Medium/Low 分类汇报**：High（bug/安全/清晰错误）必修；Medium（合理但依赖上下文）选修；Low（误报/吹毛求疵）静默丢弃。

避免重蹈 ocr 覆辙：不要用 ocr/open-code-review 跑步骤4（本仓库两次实测因路径幻觉零产出，白烧 token）。

### 主线程纪律

- 主线程**不**直接写实现代码（除非纯文档/单行修）；实现一律派发子线程
- 每步完成后用 `plan_tracker` 更新状态，进度对用户可见
- 子线程返回后，主线程**必须核验**实际改动（trust but verify），不能只信子线程汇报

## 2. 实现纪律 — TDD（通用）

> **推荐加载技能** `tdd`（加载可拿完整 red-green-refactor 工作流上下文；核心铁律已摘入下方 §2.1-2.4，不加载也不丢约束）。

遵循铁律：**没有失败测试，不写产品代码。**

### 2.1 红绿重构循环

每次只做 **一个** 垂直切片：

```
RED   → 写 1 个测试，验证它失败（必须看到失败原因正确）
GREEN → 写最小实现代码通过测试
REFACTOR → 清理，保持所有测试通过
```

**严禁水平切片**（先写完所有测试再写实现）。每个测试必须在前一个测试 GREEN 之后才写。

### 2.2 强制规则

- 测试必须先于实现代码存在
- 每个测试必须亲眼看到失败，确认失败原因正确
- 实现代码必须是最小的 —— 只够通过当前测试
- 重构时保持所有测试绿色，不得添加新行为
- 测试描述行为而非实现，使用公共接口

### 2.3 分级执行

- **新增模块 / 核心逻辑变更** → **强制** 完整 TDD
- **Bug 修复** → **强制** 先写复现测试，再修代码
- **现有代码小幅修改** → 至少补充回归测试
- **纯配置 / SQL 迁移脚本** → 豁免（但需人工验证）

### 2.4 红旗行为 — 遇到即停止

- 先写实现后补测试
- 一次生成多个测试
- 测试立即通过（没有看到失败）
- 跳过重构阶段
- "这次先跳过 TDD"

遇到以上情况：删除已有代码，从 TDD 重新开始。

- 测试失败难以定位时，加载技能：`diagnose`

## 3. 复杂设计验证（通用）

> **推荐加载技能** `prototype`（加载可拿完整原型方法论；核心铁律已摘入下方，不加载也不丢约束）。

- 涉及以下场景时，**必须先做可丢弃原型**：
  - 状态机（≥3 个状态且存在循环流转）
  - 算法逻辑（排序、预测、匹配引擎）
  - 多模块交互协议（API 契约、事件总线）
- prototype 必须输出：方案对比、选型理由、风险点
- 原型产出物归入 `openspec/changes/<name>/` 目录
- 确认后销毁原型，再进入 TDD 正式实现

## 4. 后端执行规范（Go + Gin + GORM）

### 4.0 前置条件检查

apply 启动时，先检测以下基础设施是否就绪，缺失则作为第一个子任务补齐：

- [ ] `go vet ./...` 可正常执行（0 错误）
- [ ] `golangci-lint run ./...` 可正常执行（已安装，配置文件 `.golangci.yml` 存在）
- [ ] `go test ./...` 可正常执行（即使 0 个测试用例）
- [ ] `go build ./...` 可正常编译

若 golangci-lint 未安装，作为首个子任务安装并配置：

```bash
go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@latest
```

### 4.1 质量门禁

提交前必须通过以下命令：

```bash
cd backend-go
golangci-lint run ./... && go vet ./... && go test ./... && go build ./...
```

门禁覆盖：

| 工具               | 用途                    |
| ------------------ | ----------------------- |
| `golangci-lint`    | 静态分析（staticcheck, revive, gosec 等） |
| `go vet`           | Go 官方静态检查          |
| `go test`          | 单元测试执行             |
| `go build`         | 编译检查                 |

提交前必须 100% 通过门禁。

#### 门禁分层（增量 vs 全量）

| 场景 | 后端 | 前端 | 触发 |
| ---- | ---- | ---- | ---- |
| 增量（pi extension 自动） | `golangci-lint` + `go vet` + `go build` | `pnpm lint` | 每回合 `turn_end`，软提示（[`.pi/extensions/quality-gate.ts`](../../../.pi/extensions/quality-gate.ts)） |
| 日常验证（agent 手动） | `go test ./internal/<影响包>` | `pnpm test:unit`（cmd） | 每子任务后 |
| 归档全量（§11） | `go test ./...` + `go build ./...` | `pnpm build` + `nuxi typecheck` | archive 前 |

> **边界说明**：增量 extension **不跑 `go test`**——影响包无法自动判定（codegraph affected 实测误报），全量 `go test ./...` 100s+Docker+flaky。前端增量**只跑 `pnpm lint`**——typecheck/test:unit/build 需 cmd.exe，bash hook 脆弱。完整门禁仍由 §11 归档门禁兜底。
> **运行时差异**：pi extension 仅在 pi 下自动触发；真 Claude Code / Codex 无此 extension，需手动跑增量门禁命令。

### 4.2 测试规范

> 测试框架、分层约定、`SetupTestDB` 使用模式、常见陷阱的**权威定义**见 [`standard/backend/testing.md`](standard/backend/testing.md)。本规范只保留门禁与执行纪律（§4.1、§6）。

### 4.3 golangci-lint 配置

> 启用 linters、安装、配置文件位置的**权威定义**见 [`standard/backend/lint.md`](standard/backend/lint.md)。门禁命令见 §4.1。

## 6. 集成测试规范（Go testcontainer）

> 集成测试细节（分层约定、`SetupTestDB` 使用模式、vector 列陷阱、连接重建原理）以 [`standard/backend/testing.md`](standard/backend/testing.md) 为权威。本节只规定执行纪律。

### 6.0 前置条件

- [ ] Docker Desktop / daemon 运行中（testcontainer 需启动隔离 pgvector 容器 `pgvector/pgvector:pg18-trixie`）
- [ ] 容器为进程级单例：首次调用 `testutil.SetupTestDB(t)` 启动，进程退出由 Ryuk sidecar 自动销毁，无需手动清理

### 6.1 运行方式

```bash

# 仅单元测试（跳过需要 Docker 的集成测试）
go test -short ./...
```

> AGENTS.md 约定：日常验证**只跑本次修改影响的包**，例如 `go test ./internal/domain/daily_report ./internal/platform/ws`，不跑全量 `go test ./...`。

> 编写细节（入口函数、`-short` 跳过、文件命名分层、`ReimportTestDB`、vector 列陷阱、连接重建）的**权威定义**见 [`standard/backend/testing.md`](standard/backend/testing.md)。

🛑 **DSN 安全红线（不可违反）**：`testutil` 无默认 DSN、不读环境变量，只能启动隔离容器。**禁止**重新引入任何「默认数据库连接」或「env 覆盖」机制——历史事故曾因此误连开发库执行 `TRUNCATE` 清空业务数据。

## 7. 架构体检（通用）

实现完成后，执行以下检查：

### 7.1 codegraph 代码图检查（强制）

- 每个子任务完成后必须执行：
  1. `codegraph impact <修改的符号>`
     → 影响分析：确认改动波及面无 HIGH/CRITICAL 风险被忽略
  2. `codegraph affected <改动的源文件>`
     → 变更检测：确认受影响的测试文件范围符合预期
- 若 `impact` 返回 HIGH/CRITICAL 风险，必须暂停并向用户报告，不得忽略
- **已知局限 1**：codegraph 无法追踪 Gin handler 的 `group.GET/POST(..., fn)` 注册模式，会把仅由路由注册引用的 handler 误报为「无调用者」（约 26 个误报）。删除 Gin handler 前必须用 `grep` 二次校验其是否被路由注册引用，避免误删
- **已知局限 2·顺传导链深查**：`codegraph impact` 只显示**直接调用面**，看不到跨层/跨域的**隐式传导**（如“改截断排序 → 经 LLM 聚类输入 → 打散 topic 锚定”）。若改动处于某条传导链上（查 [coupling-map.md](architecture/coupling-map.md)），必须人工顺链推导下游影响，不能只看到直接 impact 就收工。踩到/分析出新的跨功能传导耦合，**必须往 `architecture/coupling-map.md` 补一条**（含守卫测试）。
- **附注·code-review-graph 增量维护代码图（按运行时生效，不作为强制门禁）**：
  - **真 Claude Code / Codex**：`.claude/settings.json` / `.codex/hooks.json` 已配置 PostToolUse hook（`code-review-graph update --skip-flows`），自动增量维护代码图
  - **pi（主力）/ zcode**：**不读** `.claude/` `.codex/`，hook 不触发；需手动 `code-review-graph update --skip-flows` 维护代码图
  - 无论哪个运行时，code-review-graph 都**不是强制门禁**，只是 codegraph impact/affected 的数据源维护工具

### 7.2 架构合理性检查

- 加载技能 `zoom-out` 检查：
  - 新增模块与现有系统的耦合度
  - 是否引入循环依赖
  - 是否符合现有分层架构（后端：`internal/reader/`、`internal/tagmanagement/`、`internal/topicgraph/`、`internal/admin/` + `internal/platform/*`；前端：Vue 3 Composition API + Pinia stores）
- 若耦合过高，暂停并提出重构建议

## 8. 变更控制

> OpenSpec 的核心优势是灵活。apply 阶段允许按需调整 proposal/spec/design 范围，但调整须**留痕可溯**，不是偷偷改。

- **apply 阶段允许调整范围**：实现中发现原方案不合理时，直接更新对应制品（proposal/spec/design/tasks），并在 commit message 或 tasks.md 备注调整原因。不必退出 apply 走 delta。
- **大范围推翻才需另起 change**：仅当方向性变更（换技术栈、改核心目标）时，才新开 change 或 archive 旧的；局部澄清/细化/纠错一律就地更新。
- **变更程度判据（就地改 vs 重批 vs 新开 change）**：

  | 程度 | 判据 | 处理 | 与 plan mode 关系 |
  | ---- | ---- | ---- | ----------------- |
  | 局部澄清/纠错 | 单个 task 的实现细节调整、字段名修正、补充边界条件 | 就地改 spec/design/tasks + tasks.md 留痕 | 不需重新 ExitPlanMode |
  | 范围扩展 | 新增 1-2 个 task、补遗漏的需求场景 | 就地改 + tasks.md 留痕 + 通知用户 | 不需重新 ExitPlanMode，但需在回复中告知用户范围扩大 |
  | 中等重构 | 重写 >3 个 task、换核心数据结构、改 API 契约形状 | 就地改 + tasks.md 留痕 + **重新 ExitPlanMode 获用户批准** | 需重新批准（plan 核心假设变了） |
  | 方向性变更 | 换技术栈、改核心目标、推翻 proposal 的根本目标 | **新开 change** 或 archive 旧的 | 新 change 走完整 propose→apply |

  > 边界原则：**用户对范围变化有知情权**。哪怕"就地改"，只要扩展了用户当初批准的范围（新增 task、改了对外契约），必须在回复里明说，不能默默扩大。

- 禁止在代码注释里写 "TODO：后续优化" 却不记录到 tasks.md
- **归档前禁止跳过 §11 归档门禁**；验证节命令未实测通过的 change 不得 archive

## 11. 归档门禁（Archive Gate）

> 归档（openspec archive）是 SDD 流程的最终硬门禁。提交前门禁（§4.1/§5.1）覆盖代码质量；归档门禁覆盖"代码↔文档一致性 + 验证可复现"。

### 11.1 归档前置三条件（缺一不可）

1. **测试通过**：§4.1（后端）/ §5.1（前端）/ §6（集成）对应门禁命令实测通过
   - 纯文档 change 豁免代码测试，但必须跑 §11.3 的 grep 一致性校验
2. **文档同步**：§9 产出物清单全部勾选，`docs/reference/` 已反映新代码状态
3. **验证可复现**：tasks.md 的"验证"节（见 §11.2）每条命令实测零失败

### 11.2 tasks.md 验证节强制结构

每个 change 的 tasks.md **必须**以三个固定尾节收尾：

- `## N. 测试` — 列出本次 change 影响的测试命令（后端 `go test ./internal/<pkg>`、前端 `pnpm test:unit`）
- `## N+1. 文档` — 列出需要同步更新的 `docs/reference/` 文件；功能性 change 若触及 `flow/`，须声明将在 §12.2 补「变更溯源」链接（archive 后补）
- `## N+2. 验证` — 每条**必须**是"可执行命令 + 期望结果"，禁止只写"已检查"

验证节条目格式示例：

- `findstr /S /N /R /C:"<幽灵模式>" docs\reference\*.md → 零命中`
- `go test ./internal/admin/scheduler → PASS`

### 11.3 纯文档 change 的测试门禁

纯文档 change（无代码改动，如 `update-reference-docs`）：

- 豁免 `go test` / `pnpm test`
- **必须**在"验证"节附 grep 一致性校验命令（参考 `update-reference-docs` tasks.md §11）
- 校验维度：幽灵路径、幽灵调度器、幽灵命令、版本号、旧包名零残留

### 11.4 归档前自检

执行 `openspec archive` 前，必须重跑 tasks.md"验证"节全部命令，确认零失败。若归档 skill 仅数复选框，归档前由人/AI 手动补这一步。

同时跑 `bash scripts/check-standards.sh`（L1 规范验收，见 [`standard/README.md`](standard/README.md)）：A-D 段（代码规范结构、domain 白名单、双主题、防孤立引用）归档前必须零失败；E 段（flow 变更溯源链接）针对 archive 区，归档后校验（见 §12.3）。

## 12. 文档流转（Archive 即家 → Flow 反向溯源）

> §11 管 archive **前**的门禁；§12 管 archive **后**的活文档更新。archive 区从「中转站」升级为「永久归档家」，靠 `reference/flow/` 反向链接串联，省掉每次手动开版本号、搬文件的麻烦。

### 12.1 两段式流转

| 阶段 | 位置 | 责任节点 | 状态 |
|------|------|----------|------|
| ① 开发中 | `openspec/changes/<change>/` | propose → apply | 临时，可反复修改 |
| ② 归档（永久家） | `openspec/changes/archive/<date>-<change>/` | `openspec sync` + `openspec archive` | 永久归档，不再搬走 |
| ③ Flow 反向溯源 | `docs/reference/flow/<功能>.md` | archive 后由 change 作者补「变更溯源」行 | 活文档，链接回 archive |

> `docs/v1.x/` 里程碑目录**降级为可选**：平时 archive 即终点；只有要发版/做主题合集时，才批量把 archive 区相关 change 收进 `docs/v1.x/changes/`（操作见 §12.4）。不再每个 change 强制归类。

### 12.2 变更溯源链接（archive 后强制）

`openspec archive` 完成后，change 作者**必须**在受影响的 `docs/reference/flow/<功能>.md` 尾部「变更溯源」表追加一行，链接回 archive 目录：

```markdown
## 变更溯源

| 日期 | 变更 | 摘要 | 归档位置 |
|------|------|------|----------|
| 2026-06-14 | scheduler-cron | 定时任务改 cron 驱动 | [`openspec/changes/archive/2026-06-14-scheduler-cron`](../../../openspec/changes/archive/2026-06-14-scheduler-cron) |
```

约定：

- 一个 change 可能动多个 flow，每个受影响的 flow 都要补一行
- 「归档位置」列**必须**包含 archive 目录全名（`<date>-<change>`），供 `scripts/check-standards.sh` E 段静态校验
- 纯文档 change / 不触及任何 flow 的 change：豁免（在 tasks.md「文档」节注明「无 flow 影响」）
- 链接用相对路径（flow 文档到 archive：`../../../openspec/changes/archive/<date>-<change>`），便于本地跳转

### 12.3 archive 后校验

补完变更溯源链接后，再跑一次门禁确认串联成立：

```bash
bash scripts/check-standards.sh
```

E 段（flow 变更溯源链接）必须零失败。校验范围：新流程生效日（`2026-06-29`）之后的 archive change 必须被某 flow 文档引用；历史存量免校验，避免一次性爆 FAIL。

### 12.4 里程碑（可选，发版时才用）

`docs/v1.x/` 不再是每次归档的必经站。仅当需要发布版本/整理主题合集时，才把 archive 区相关 change 批量收进里程碑：

```bash
# 批量归类（保留 git 历史），按主题挑
mkdir -p docs/v1.x/changes
git mv openspec/changes/archive/<date>-<change> docs/v1.x/changes/[<分组>/]
```

里程碑目录沿用既有结构（`SUMMARY.md` + `changes/[<分组>/]`，命名 `<date>-<name>`）。archive 是永久家，归类后 archive 区对应 change **保留不删**（里程碑是快照副本视角，archive 是证据原件）。

### 12.5 流转完整性自检

- [ ] archive 区的 change 已在受影响 flow 的「变更溯源」表补链接
- [ ] `bash scripts/check-standards.sh` E 段零失败
- [ ] `docs/reference/` 已反映新代码状态（§11 归档门禁验证节零失败）
- [ ] （可选）发版时 `docs/v1.x/SUMMARY.md` 变更清单与 `changes/` 实际目录一致
