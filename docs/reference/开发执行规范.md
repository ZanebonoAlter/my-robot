# OpenSpec 通用执行规范（Apply 阶段强制遵循）

> 本文件为所有 Proposal 的默认施工纪律。
> 被 `@执行规范.md` 引用的 Proposal，必须在 Engineering Standards 章节完整并入以下内容。

## 0. 适用范围

本规范覆盖以下两套活跃代码栈：

| 栈   | 项目路径        | 构建工具 | 语言        |
| ---- | --------------- | -------- | ----------- |
| 后端 | `backend-go/`   | Go       | Go 1.25     |
| 前端 | `front/`        | pnpm     | TypeScript  |

测试分层（权威文档：[`standard/backend/testing.md`](standard/backend/testing.md) + [`standard/frontend/testing.md`](standard/frontend/testing.md)）：

| 层级         | 后端方案                                              | 前端方案                     |
| ------------ | ----------------------------------------------------- | ---------------------------- |
| 单元测试     | 内存 SQLite（`glebarez/sqlite`），无 pgvector 依赖    | Vitest + happy-dom           |
| 集成测试     | testcontainer pgvector（`testutil.SetupTestDB`，需 Docker） | Playwright E2E               |

> 后端集成测试已从历史 Python 套件迁移到 Go testcontainer 方案（见 §6），不再有独立的 Python 测试目录。

apply 启动时，根据变更所涉及的项目栈，对应执行相应章节的前置检查与质量门禁。

## 0.5 文档归属规则（写文档该放哪）

> 这是一份运行架构 harness 的导航：写的文档内容不同，归属层也不同。放错层会导致权威散落、规范与流程混在一起。

| 写的内容 | 归属目录 | 说明 |
|---------|---------|------|
| 代码怎么写、包结构、双主题、lint/测试配置 | `docs/reference/standard/{frontend,backend}/` | **唯一权威源**；AGENTS.md 只留红线速查 + 深链 |
| 业务链路怎么跑、状态流转、前后端协作 | `docs/reference/flow/<大功能>.md` | 配 mermaid，跨端，按大功能切 |
| 架构定位、骨架、运行时、链路追踪 | `docs/reference/architecture/` | 不写流程细节，流程链接到 flow/ |
| 详细设计索引（业务域 → 流程 → 代码入口） | `docs/reference/architecture/map.md` | 导航总图 |
| 执行流程 / 门禁 / 归档纪律 | 本文件 | 「什么时候做什么」 |
| 运维（配置、部署） | `docs/reference/configuration.md`、`deployment.md` | 根目录平铺 |

**防孤立约束**：`standard/` 下每个文档必须被对应 `AGENTS.md` 或 `standard/README.md` 引用；`scripts/check-standards.sh`（L1）在归档前校验此约束（见 §11.4）。

## 2. 实现纪律 — TDD（通用）

> **实现前必须加载技能：** `tdd`

遵循铁律：**没有失败测试，不写产品代码。**

### 2.1 红绿重构循环

每次只做 **一个** 垂直切片：

```
RED   → 写 1 个测试，验证它失败（必须看到失败原因正确）
GREEN → 写最小实现代码通过测试
REFACTOR → 清理，保持所有测试通过
```

**严禁水平切片**（先写完所有测试再写实现）。每个测试必须在前一个测试 GREEN 之后才写。

### 2.2 强制规则

- 测试必须先于实现代码存在
- 每个测试必须亲眼看到失败，确认失败原因正确
- 实现代码必须是最小的 —— 只够通过当前测试
- 重构时保持所有测试绿色，不得添加新行为
- 测试描述行为而非实现，使用公共接口

### 2.3 分级执行

- **新增模块 / 核心逻辑变更** → **强制** 完整 TDD
- **Bug 修复** → **强制** 先写复现测试，再修代码
- **现有代码小幅修改** → 至少补充回归测试
- **纯配置 / SQL 迁移脚本** → 豁免（但需人工验证）

### 2.4 红旗行为 — 遇到即停止

- 先写实现后补测试
- 一次生成多个测试
- 测试立即通过（没有看到失败）
- 跳过重构阶段
- "这次先跳过 TDD"

遇到以上情况：删除已有代码，从 TDD 重新开始。

- 测试失败难以定位时，加载技能：`diagnose`

## 3. 复杂设计验证（通用）

> **进入原型阶段前必须加载技能：** `prototype`

- 涉及以下场景时，**必须先做可丢弃原型**：
  - 状态机（≥3 个状态且存在循环流转）
  - 算法逻辑（排序、预测、匹配引擎）
  - 多模块交互协议（API 契约、事件总线）
- prototype 必须输出：方案对比、选型理由、风险点
- 原型产出物归入 `openspec/changes/<name>/` 目录
- 确认后销毁原型，再进入 TDD 正式实现

## 4. 后端执行规范（Go + Gin + GORM）

### 4.0 前置条件检查

apply 启动时，先检测以下基础设施是否就绪，缺失则作为第一个子任务补齐：

- [ ] `go vet ./...` 可正常执行（0 错误）
- [ ] `golangci-lint run ./...` 可正常执行（已安装，配置文件 `.golangci.yml` 存在）
- [ ] `go test ./...` 可正常执行（即使 0 个测试用例）
- [ ] `go build ./...` 可正常编译

若 golangci-lint 未安装，作为首个子任务安装并配置：

```bash
go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@latest
```

### 4.1 质量门禁

提交前必须通过以下命令：

```bash
cd backend-go
golangci-lint run ./... && go vet ./... && go test ./... && go build ./...
```

门禁覆盖：

| 工具               | 用途                    |
| ------------------ | ----------------------- |
| `golangci-lint`    | 静态分析（staticcheck, revive, gosec 等） |
| `go vet`           | Go 官方静态检查          |
| `go test`          | 单元测试执行             |
| `go build`         | 编译检查                 |

提交前必须 100% 通过门禁。

### 4.2 测试规范

> 测试框架、分层约定、`SetupTestDB` 使用模式、常见陷阱的**权威定义**见 [`standard/backend/testing.md`](standard/backend/testing.md)。本规范只保留门禁与执行纪律（§4.1、§6）。

### 4.3 golangci-lint 配置

### 4.4 后端代码规范

## 6. 集成测试规范（Go testcontainer）

> 集成测试细节（分层约定、`SetupTestDB` 使用模式、vector 列陷阱、连接重建原理）以 [`standard/backend/testing.md`](standard/backend/testing.md) 为权威。本节只规定执行纪律。

### 6.0 前置条件

- [ ] Docker Desktop / daemon 运行中（testcontainer 需启动隔离 pgvector 容器 `pgvector/pgvector:pg18-trixie`）
- [ ] 容器为进程级单例：首次调用 `testutil.SetupTestDB(t)` 启动，进程退出由 Ryuk sidecar 自动销毁，无需手动清理

### 6.1 运行方式

```bash
cd backend-go

# 含集成测试（需 Docker）：testcontainer 自动启动隔离 pgvector 容器
go test ./...

# 仅单元测试（跳过需要 Docker 的集成测试）
go test -short ./...
```

> AGENTS.md 约定：日常验证**只跑本次修改影响的包**，例如 `go test ./internal/domain/daily_report ./internal/platform/ws`，不跑全量 `go test ./...`。

### 6.2 编写规范

> 编写细节（入口函数、`-short` 跳过、文件命名分层、`ReimportTestDB`、vector 列陷阱、连接重建）的**权威定义**见 [`standard/backend/testing.md`](standard/backend/testing.md)。

🛑 **DSN 安全红线（不可违反）**：`testutil` 无默认 DSN、不读环境变量，只能启动隔离容器。**禁止**重新引入任何「默认数据库连接」或「env 覆盖」机制——历史事故曾因此误连开发库执行 `TRUNCATE` 清空业务数据。

## 7. 架构体检（通用）

实现完成后，执行以下检查：

### 7.1 codegraph 代码图检查（强制）

- 每个子任务完成后必须执行：
  1. `codegraph impact <修改的符号>`
     → 影响分析：确认改动波及面无 HIGH/CRITICAL 风险被忽略
  2. `codegraph affected <改动的源文件>`
     → 变更检测：确认受影响的测试文件范围符合预期
- 若 `impact` 返回 HIGH/CRITICAL 风险，必须暂停并向用户报告，不得忽略
- **已知局限**：codegraph 无法追踪 Gin handler 的 `group.GET/POST(..., fn)` 注册模式，会把仅由路由注册引用的 handler 误报为「无调用者」（约 26 个误报）。删除 Gin handler 前必须用 `grep` 二次校验其是否被路由注册引用，避免误删
- **附注**：code-review-graph 作为 PostToolUse hook 自动触发（`.claude/settings.json` / `.codex/hooks.json` 已配置 `code-review-graph update --skip-flows`），用于增量维护代码图，不作为强制门禁

### 7.2 架构合理性检查

- 加载技能 `zoom-out` 检查：
  - 新增模块与现有系统的耦合度
  - 是否引入循环依赖
  - 是否符合现有分层架构（后端：`internal/reader/`、`internal/tagmanagement/`、`internal/topicgraph/`、`internal/admin/` + `internal/platform/*`；前端：Vue 3 Composition API + Pinia stores）
- 若耦合过高，暂停并提出重构建议

## 11. 归档门禁（Archive Gate）

> 归档（openspec archive）是 SDD 流程的最终硬门禁。提交前门禁（§4.1/§5.1）覆盖代码质量；归档门禁覆盖"代码↔文档一致性 + 验证可复现"。

### 11.1 归档前置三条件（缺一不可）

1. **测试通过**：§4.1（后端）/ §5.1（前端）/ §6（集成）对应门禁命令实测通过
   - 纯文档 change 豁免代码测试，但必须跑 §11.3 的 grep 一致性校验
2. **文档同步**：§9 产出物清单全部勾选，`docs/reference/` 已反映新代码状态
3. **验证可复现**：tasks.md 的"验证"节（见 §11.2）每条命令实测零失败

### 11.2 tasks.md 验证节强制结构

每个 change 的 tasks.md **必须**以三个固定尾节收尾：

- `## N. 测试` — 列出本次 change 影响的测试命令（后端 `go test ./internal/<pkg>`、前端 `pnpm test:unit`）
- `## N+1. 文档` — 列出需要同步更新的 `docs/reference/` 文件
- `## N+2. 验证` — 每条**必须**是"可执行命令 + 期望结果"，禁止只写"已检查"

验证节条目格式示例：

- `findstr /S /N /R /C:"<幽灵模式>" docs\reference\*.md → 零命中`
- `go test ./internal/admin/scheduler → PASS`

### 11.3 纯文档 change 的测试门禁

纯文档 change（无代码改动，如 `update-reference-docs`）：

- 豁免 `go test` / `pnpm test`
- **必须**在"验证"节附 grep 一致性校验命令（参考 `update-reference-docs` tasks.md §11）
- 校验维度：幽灵路径、幽灵调度器、幽灵命令、版本号、旧包名零残留

### 11.4 归档前自检

执行 `openspec archive` 前，必须重跑 tasks.md"验证"节全部命令，确认零失败。若归档 skill 仅数复选框，归档前由人/AI 手动补这一步。

同时跑 `bash scripts/check-standards.sh`（L1 规范验收，见 [`standard/README.md`](standard/README.md)）：代码规范结构、domain 白名单、双主题、防孤立引用检查零失败。

## 12. 文档流转（Archive → 里程碑 → Reference）

> §11 管 archive **前**的门禁；§12 管 archive **后**的归类与活文档更新。两者衔接构成 SDD 完整文档链。

### 12.1 三段式流转

SDD 文档按三段流转，每段有固定位置与责任节点：

| 阶段 | 位置 | 责任节点 | 状态 |
|------|------|----------|------|
| ① 开发中 | `openspec/changes/<change>/` | propose → apply | 临时，可反复修改 |
| ② 归档中转 | `openspec/changes/archive/<date>-<change>/` | `openspec archive` | 中转，非终点 |
| ③ 里程碑归类 | `docs/v1.x/changes/<date>-<change>/` | 手动移动 | 里程碑内永久归档 |
| ④ Reference 更新 | `docs/reference/*` | 里程碑收尾时手动同步 | 活文档，反映最终代码 |

### 12.2 archive 是中转，不是终点

`openspec/changes/archive/` 仅作临时中转区（openspec CLI 的 archive 路径写死于此）。每个归档 change **必须**在当前里程碑收尾前移入 `docs/v1.x/changes/`，不得长期滞留在 archive 区。

归类操作：

```bash
# 从 archive 移动到当前里程碑（保留 git 历史）
git mv openspec/changes/archive/<date>-<change> docs/v1.3.4-easy-use/changes/
```

### 12.3 里程碑目录统一结构

`docs/v1.x/` 固定结构：

| 子目录 | 用途 | 必需 |
|--------|------|------|
| `SUMMARY.md` | 里程碑总览：变更清单 + 主题分组 + 完成标准 | 是 |
| `changes/` | 从 openspec archive 归类来的 change（注意复数） | 是 |
| `changes/<分组>/` | 按主题归类的多 change 集合（如 `dead-code-clean/`、`test-standard/`），可选 | 否 |
| `other/` | 尚未归入正式分组的零散 change | 否 |
| `design/` | 跨 change 的设计文档 | 否 |
| `debug/` | 调试记录 | 否 |

命名约定：

- 顶层 change 目录用 openspec archive 的 `<date>-<name>` 格式（如 `2026-06-14-scheduler-cron`）
- 二级分组目录用主题名（无日期前缀，如 `dead-code-clean`）
- 里程碑根目录用 `v<版本号>-<主题>`（如 `v1.3.4-easy-use`）

### 12.4 Reference 更新节点

`docs/reference/`（活文档）在**里程碑收尾时**统一更新，而非每个 change 都改：

- 功能性 change：reference 在里程碑收尾时同步该里程碑引入的新代码状态
- 纯文档修正 change（如 `update-reference-docs`）：本身就是 reference 更新，归档即生效
- 跨里程碑长期滞后的 reference：可单独开一个纯文档 change 走 §11.3 路径补救

### 12.5 流转完整性自检

里程碑收尾前确认：
