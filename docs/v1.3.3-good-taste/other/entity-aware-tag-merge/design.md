## Context

当前标签合并建议系统依赖纯 embedding 余弦相似度（阈值 0.92）来判断两个标签是否应该合并。经过数据分析（5,288 条 pending），发现即使在 0.92+ 区间，纯 embedding 仍无法区分以下模式：

| 模式 | 占比 | 示例 | 应合并？ |
|------|------|------|----------|
| 文本近似（仅空格/标点/简写差异）| ~30% | "软银集团超越丰田成为日本市值最高企业" vs "...公司" | ✅ |
| 同一事件不同信息源 | ~25% | "SpaceX公开S-1招股书" vs "SpaceX首次公开募股" | ✅ |
| 数值不同但主题相同 | ~20% | "沪深两市成交额突破1万亿元" vs "...1.5万亿元" | ❌ |
| 相关但独立的事件 | ~15% | "PettiChat推出AI宠物项圈" vs "PettiChat构建动物行为世界模型" | ❌ |
| 上下位/包含关系 | ~10% | "伊朗伊斯兰革命卫队海军" vs "伊朗伊斯兰革命卫队" | ❌ |

嵌入匹配对模式①②有效，但对③④⑤无能为力。本设计通过提取标签中的**命名实体**和**数值**来过滤掉③④⑤。

### 现有架构

```
TagMatch() / runFullScan()
  → FindSimilarTags() → embedding cosine similarity ≥ LowSimilarity (0.92)
    → 直接写入 tag_merge_suggestions
```

目标架构：

```
TagMatch() / runFullScan()
  → FindSimilarTags() → embedding cosine similarity ≥ LowSimilarity (0.92)
    → EntityFilter(labelA, labelB)  ← 新增
      → PASS: 实体有交集且数值一致 → 写入 suggestion
      → REJECT: 数值不同或实体无交集 → 跳过
```

## Goals / Non-Goals

**Goals:**
- 在增量和全量扫描路径中，对 embedding 匹配的候选对增加实体+数值过滤
- 将模式③（数值不同）的误报率降低 80%+
- 将模式④⑤的误报率降低 50%+
- 纯 Go 实现，不引入 Python/外部 NLP 依赖

**Non-Goals:**
- 完整的主谓宾/依存句法分析
- 替换 embedding 匹配（仅作为前置过滤）
- 修改已存在的建议记录
- 前端 UI 变更

## Decisions

### Decision 1: 实体提取方案 — 正则 + 规则，不依赖 NLP 库

**选择**: 纯 Go 正则+规则实现实体提取

**备选方案**:
- A) 引入 jieba Go 绑定（gojieba）→ 额外 CGO 依赖，部署复杂
- B) 调用外部 NLP API → 增加延迟和外部依赖
- C) 正则+规则 → 零依赖，覆盖率够用

**理由**: 标签文本通常是短语而非长句，结构相对规则。命名实体主要是人名、机构名、地名、产品名，数值主要是金额、百分比、数量。对于标签这个场景，正则+规则足以覆盖 80%+ 的 cases。

**提取内容**:
- **数值**: 正则匹配数字+单位（亿、万、%、美元、亿元、万亿元、点等）
- **命名实体**: 利用标签已有的 category 和 slug 信息辅助判断，结合正则匹配大写英文（产品/机构名）、中文姓名模式（2-4字的已知实体）
- **关键词交集**: 简单分词（按空格/标点/英文边界切分），计算关键词重叠率

### Decision 2: 过滤策略 — 数值不同直接排除，实体无交集直接排除

**规则**:
1. 提取两个标签的数值集合 `numsA`, `numsB`
2. 如果 `numsA` 和 `numsB` 都非空且不相等 → **REJECT**（数值不同的新闻不应合并）
3. 提取两个标签的实体/关键词集合 `entitiesA`, `entitiesB`
4. 如果交集为空 → **REJECT**（无共同实体的标签不应合并）
5. 其他情况 → **PASS**（交给下游处理）

**理由**: 这是最保守的策略——只在明确有证据表明不应合并时才排除，不会误杀。

### Decision 3: 提取器位置 — 独立包 `tagging/entityfilter`

**选择**: 在 `internal/domain/tagging/entityfilter/` 下新建包

**理由**:
- 与现有 embedding/tag_merge 逻辑解耦
- 可独立测试
- 调用时只传入两个 label 字符串，返回 bool（pass/reject）+ 可选的拒绝原因

## Risks / Trade-offs

- [正则实体提取对中文支持有限] → 首期只处理英文实体（大写字母开头）和数值，中文实体用关键词交集兜底。后续可迭代升级提取器。
- [过度过滤可能漏掉真正应合并的对] → 采用保守策略：只在数值不同或实体完全无交集时才排除。宁可多留一些噪音，不可误杀。
- [性能开销] → 正则提取是 O(1) 操作（短文本），对全量扫描几乎无影响。
